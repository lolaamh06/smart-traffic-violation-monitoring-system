Unnormalized Form (UNF)

In UNF, all data columns are placed into a single flat structure `TRAFFIC_DATA`. This layout contains severe data redundancy and anomalies.

Anomalies Present:
  • Red Highlight (Redundant vehicle/owner data): Owner names, phone numbers, and emails are repeated for every single violation of the same vehicle.
  • Amber Highlight (Officer and Location detail redundancies): Officer details and location coordinates are repeated, instead of referencing unique keys.

First Normal Form (1NF)

Rule: Atomic values (no repeating groups / multi-valued fields) and a designated Primary Key.

1NF Change: In our system, the route coordinates for safe route searches could be stored as an array or JSON string. To satisfy 1NF, we extract route waypoints and searches into two structured tables (`ROUTE_SEARCHES` and a junction relationship table or structured schema) ensuring every column contains single, atomic values.

All other fields in `TRAFFIC_DATA` are already atomic. The flat table remains, but now with a defined Primary Key `violation_id` + `vehicle_reg` + `officer_badge` composite key.

Second Normal Form (2NF)

Rule: Must be in 1NF, and all non-key attributes must show Full Functional Dependency on the primary key (no partial dependency).

2NF Extraction: In 1NF, `owner_name` depends only on `vehicle_reg`, not the rest of the key. Similarly, `officer_name` depends only on `officer_badge`. We extract them into dedicated tables `VEHICLES` and `OFFICERS` to eliminate these partial dependencies.

We split our design into distinct tables with single Primary Keys:

  • VEHICLES (vehicle_id, reg_number, owner_name, owner_phone, owner_email, vehicle_type, created_at)
  • OFFICERS (officer_id, badge_number, name, zone, username, password_hash, created_at)
  • VIOLATIONS (violation_id, vehicle_id, officer_id, location_id, type_id, violation_time, evidence_image_url, status, created_at)

Third Normal Form (3NF)

Rule: Must be in 2NF, and must have No Transitive Dependencies (non-key attributes should not depend on other non-key attributes).

3NF Extraction: In the `VIOLATIONS` table, `base_fine` is determined by `violation_type` (which is a non-key attribute in the parent table). This is a transitive dependency: `violation_id` → `violation_type` → `base_fine`. We resolve this by extracting `VIOLATION_TYPES` into its own table, keeping only a foreign key reference inside `VIOLATIONS`.

Our final 3NF schema consists of 7 completely independent, normalized tables:

  1. VEHICLES: Vehicle profiles & owner contact data.
  2. OFFICERS: Officer profile records and police credentials.
  3. LOCATIONS: Geolocation zones (Silk Board, MG Road, etc.).
  4. VIOLATION_TYPES: Violation categories and base fines (INR).
  5. VIOLATIONS: Logged violation events (Central Fact Table).
  6. FINES: Invoicing and collection records (1:1 with violations).
  7. ROUTE_SEARCHES: Geolocation risk search log.

Normalization Summary

This table maps redundancies detected in the Unnormalized Form (UNF) to their formal database design resolutions.

Original Redundancy Issue (UNF) Violation Level Resolution Strategy Final Target Table
Owner name & phone repeated for every violation. 2NF (Partial Dependency) Extract into a single vehicle profiles table. Reference via foreign key `vehicle_id`. vehicles
Officer names & login details repeated. 2NF (Partial Dependency) Extract to accounts metadata store. Reference via `officer_id`. officers
Coordinates & location zones replicated across records. 2NF (Partial Dependency) Group geocodes and locations. Reference via `location_id`. locations
Base fine mapping duplicated on individual violations. 3NF (Transitive Dependency) Extract to catalog table mapping violation type name → base fine value. Reference via `type_id`. violation_types
Multiple route waypoint coordinates stored inside route searches array. 1NF (Repeating Groups) Store route nodes in normalized sub-array structure or related entries. route_searches
